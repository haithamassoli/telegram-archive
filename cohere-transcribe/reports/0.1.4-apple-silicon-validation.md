# 0.1.4 Apple Silicon (MPS) Validation

Date: 2026-08-31

## Scope

This exercise validated the existing Apple MPS device path on physical hardware
and decided whether Apple Silicon can be declared supported. It was a validation
exercise, not a port: the default outcome was zero runtime source changes, and
that is the outcome. Nothing under `src/` was modified. `docs/apple-silicon-plan/`
holds the plan and its milestone breakdown.

The MPS path was already written correctly. `pick_device` returns `"mps"` from
`--device auto`, `empty_device_cache` handles it, `PYTORCH_ENABLE_MPS_FALLBACK=1`
is set before the torch import, pinned memory and CUDA events are gated off, the
OOM classifier matches the MPS allocator message, and the console suppresses CUDA
memory telemetry off CUDA. Every required wheel is published for
`macosx_*_arm64`; nothing built from source.

Two contingent runtime edits were available and neither was warranted. The
`PYTORCH_ALLOC_CONF` question resolved in favour of leaving `_environment.py`
alone, and no measurement failure reopened the runtime-change path.

Additions are confined to a kernel probe, a corpus builder, a CI job, tests,
documentation, and this report.

## Supported Boundary

Apple Silicon, macOS 14 or newer. PyTorch 2.11 requires macOS 14 for MPS and the
TorchCodec arm64 wheel targets `macosx_14_0_arm64`. Intel Macs are out of scope:
no MPS, and no measured CPU-only claim.

Validated on M3 with 24 GB unified memory; lower-memory and other M-series
systems are compatibility targets, not release-tested.

## Build Sequence Adaptations

`docs/development.md` now records these; they are repeated here because they
change what evidence is admissible.

1. `python -m venv` has no interpreter on a stock macOS PATH, and `python3` is
   3.14.6, outside `requires-python`. The clean venv was created with the pinned
   3.12 from `.python-version`.
2. `rm -rf "$WHEEL_TEST"` was postponed until all hardware validation finished,
   because it deletes the only installed wheel the measurements depend on.
3. The two blocks in Clean-Wheel Validation are order-critical.
   `scripts/smoke_clean_audio.py` fails if `auditok`, `onnxruntime`,
   `silero_vad`, `torchaudio`, or `uroman` is importable, and the extras block

   and cannot be re-run in that environment afterwards.

The plan named two adaptations. The third was found during execution.

## Kernel Probe

`scripts/mps_kernel_probe.py`, run paired under `PYTORCH_ENABLE_MPS_FALLBACK=0`
and `=1`. The probe can veto a precision, never approve one.

| Operation | FP16 max abs | BF16 max abs |
|---|---:|---:|
| matmul | 1.110e-01 | 8.228e-01 |
| scaled_dot_product_attention | 3.715e-04 | 3.025e-03 |
| softmax | 3.062e-05 | 2.108e-04 |
| layernorm | 5.737e-03 | 4.784e-02 |

No veto in either run. **The paired runs produced identical result rows** — same
error figures, same statuses — which is the finding the pairing exists to
produce: no operation silently relocated to CPU at fallback 1, because none
raised at fallback 0. Only the timing lines differ between the two runs, as
timings do.

Large-matmul timing showed no BF16 emulation signature on this part. Across four
recorded probe executions, bf16/fp16 ranged 0.99 to 1.03 and bf16/fp32 ranged
0.88 to 0.93 — BF16 is at parity with FP16 and slightly faster than FP32, which
is the opposite of the emulation signature. That is an M3 result; earlier
M-series parts emulate BF16 through FP32, which is why `auto` does not dispatch
on it.

Relative-error figures are inflated by the probe's clamped denominator on
near-zero reference entries and are reported, not graded. Absolute error is the
meaningful column.

## Precision

Full detail in the Apple Silicon section of `docs/performance.md`.

MPS FP16 output was byte-identical to CPU FP32 on all 8 corpus files, with a
cross-arm CER of 0.000%, before any normalization. The output JSON matched field
for field: same segment count, same segment start and end to the microsecond,
same word timestamps, same cue boundaries, same per-segment generated-token
counts. Both arms scored 19.72% WER and 4.12% CER against the corpus reference
transcripts, identical to the digit.

All 14 admissible invocations produced byte-identical output while wall time
moved 30% and peak RSS moved 3 GiB.

The pass condition was that divergence from CPU FP32 be explainable as precision
rather than corruption. There is no divergence to explain. No NaN, Inf, empty
segment, empty transcript, OOM retry, truncation retry, repetition-guard trip, or
decoder fallback occurred in any run.

### `auto` is unchanged

`runtime/engine.py:83` stays FP16 on MPS and `tests/test_cli.py:220` is
untouched. This is observed rather than inferred: a dedicated `--dtype auto` run
produced a banner character-identical to the explicit FP16 arm, with
`configuration.dtype="auto"` resolving to `resolved_configuration.dtype="fp16"`
on device `mps`.

Changing `auto` would require BF16 measurements across M-series generations,
which this exercise did not have and which remain out of scope. A default that
dispatches on hardware nobody measured is not a measured default.

## Platform Assumptions

### Word alignment on device

A real `--alignment word` run on MPS completed on both language arms. The console
printed the word variant of the stage banner and `aligner loaded in 32s` cold,
`3s` warm. All 139 emitted words across 8 files were monotonic and in bounds,
every one carrying `timing_source: "ctc"` with `fallback_alignment_segments == 0`
— real MPS emissions through `forced_align`, not fallback timings.
`--align-dtype fp16` is correctly rejected off CUDA with
`--align-dtype fp16 is supported only with CUDA`, so MMS runs FP32 here.

### Output locks

The lease is non-blocking and per output stem, and both properties hold.

1. While A held the lock, B on the same stem exited 1 with the message body
   `Another transcription process owns output set <identity> (lock
   /tmp/cohere-transcribe-501/outputs.lock, byte <offset>)`, and the offset
   matched an independent computation for that stem.
2. **B's entire output was one blank line and the input-validation stage
   banner.** A grep for weight-loading or later-stage markers found none. B's
   median wall was 4.9s against A's median ASR load of 16s, and A was still alive
   when B returned. A contender never pays a 2B model load to discover
   contention.
3. A fresh B on the same stem after A exited succeeded and wrote all outputs.
4. Two processes on different stems in one output directory both succeeded, with
   28.4s of overlap at distinct byte offsets in the one registry file.

The registry resolves to `/private/tmp/cohere-transcribe-501/outputs.lock`;
`/tmp` is a symlink to `/private/tmp` on macOS. The directory is created at 0700
and the lock file at 0600, both owned by the running uid. Deleting the directory
and re-running recreated it cleanly at new inodes with identical permissions,
which is the behavior macOS periodic pruning requires. Setting the directory to
0755 correctly aborted a run during input validation, so `_validate_lock_directory`
is live on macOS rather than a Linux-only path.

One documentation note: the plan quotes the error with a `RuntimeError: ` prefix.
The message body is byte-for-byte correct, but that prefix never reaches stderr.
The CLI translates the exception down to a bare `SystemExit(str)`, so stderr
carries the message alone with exit 1 and no traceback.

### Audio backends

`--audio-backend torchcodec` and `--audio-backend ffmpeg` both decoded, and
`auto` resolved to TorchCodec rather than falling through to the subprocess path,
confirmed from the run's own reported backend rather than from source. mp3, m4a
and 44.1 kHz stereo WAV all decoded under `auto` with no fallback marker.

Per-file FFmpeg recovery is real and was exercised: a truncated faststart m4a
that TorchCodec rejects decoded through FFmpeg while a good file in the same
batch stayed on TorchCodec, and the batch completed. The rejection string is
recorded verbatim in the output JSON as `source.decode_fallback_reason`.

TorchCodec 0.14.0 selects its FFmpeg-8 shim and links Homebrew's ffmpeg 8.1.1
shared libraries directly. There is no vendored second FFmpeg; the decoder and
the subprocess fallback share one installation.

Finding a TorchCodec-hostile file took eight candidates, seven of which behaved
identically on both paths: header-less streaming WAV, a WAV with an invalid
data-chunk size, raw ADTS AAC, an MP3 with random bytes prepended, Ogg/Opus, and
plain mp3 and m4a. That is unsurprising given the shared libav.

### `PYTORCH_ALLOC_CONF`

`_environment.py` sets `PYTORCH_ALLOC_CONF=expandable_segments:True`, a CUDA
allocator key. On MPS it is **inert, not merely tolerated**. With the variable
set versus unset, a real MPS workload produced zero warnings under
`-W always`, zero bytes of stderr in both, and byte-identical allocator counters.
Values that would raise in the CUDA parser exited 0 with empty stderr, so nothing
parses the key at all on this build; the MPS allocator reads a disjoint
`PYTORCH_MPS_*` namespace.

The plan made a `_environment.py` edit contingent on the allocator complaining.
It does not complain, so **no edit was made**. The key confers no benefit here
either, but it is dead weight rather than a hazard, and the plan authorizes an
edit only on failure.

### CLI/API parity

Four arms, `{ar, en} × {segment, word}`. The API re-ran into the same output
directory and profile path the CLI had used, so the configuration comparison was
total with no field excused.

All 64 published files were byte-identical by sha256. 278 words, 16 segments and
35 cues compared equal by exact tuple comparison with no float tolerance. The
`resolved_configuration`, `configuration`, `models`, `implementation` and
`environment` blocks were deep-equal, and `models.asr.id`, `.revision` and
`.format` matched the API's provenance object.

Wall-clock timings were measured and printed but never compared for equality;
they differed in both directions. `peak_cuda_allocated_gib` and
`peak_cuda_reserved_gib` are 0.0 on MPS by design and were equal, so parity is
unaffected.

### Reusable-model lifecycle

All four behaviors were observed, with every run reporting `ok=True` and no
errors, checked first so that an error-path eviction could not be mistaken for
the intended one.

The decisive contrast is the second call's ASR load time: **0.000s in segment
mode, where the model is retained, against 9.634s in word mode, where alignment
evicted it and the next call reloaded**. Both one-shot `transcribe()` calls
reloaded, at 4.634s and 4.066s, confirming the one-shot cleanup path.

Device-side counters made the word-mode eviction directly visible: MPS allocated
memory fell from 3.848 GiB to 1.175 GiB exactly at the aligner load, and returned
to 0.000 at each call's end, while segment mode held 3.848 GiB across both calls
and released only at `close()`.

### Process RSS is the wrong instrument on MPS

Two independent milestones reproduced this. Model weights live in Metal
unified-memory buffers owned by the MPS caching allocator, not in resident host
pages. Sampling process RSS showed no drop at the alignment boundary and pure
noise across the one-shot cleanup, and RSS for identical work with byte-identical
output varied between 5.29 and 8.30 GiB.

RSS is reported in `docs/performance.md` because the plan asks for it, but no
memory conclusion rests on it. Device-side sampling peaked at 3.93 GiB allocated
and 4.33 GiB driver-allocated against a 17.76 GiB recommended budget.

## BF16 Characterization

Optional, never release-blocking. Its only job was to decide whether
`--dtype bf16` should be documented as an M3-validated explicit option.

**It should not.** BF16 misses one of the three criteria, so it is recorded as a
measured limitation of BF16 on this platform — a finding about the flag, not an
absence of difference — and the flag stays undocumented.

| Criterion | Bar | Measured | Verdict |
|---|---|---|---|
| Median wall time | ≤ 110% of FP16 | 109.0% pooled, 98.7% in the quiet block | Pass, with 1.0 pp of margin |
| No NaN, empty segment, or repetition-guard trip that FP16 does not also produce | — | Zero anomalies across 43 invocations | Pass |
| CER divergence from CPU FP32 | ≤ 0.5 pp above FP16's | **0.5794%** against FP16's 0.0000% | **Fail by 0.0794 pp** |

The divergence is a single deterministic word substitution in one English clip:
BF16 emits `dishes with the` where both CPU FP32 and MPS FP16 emit `dishes, the`.
It reproduced identically across ten repeats, so it is a stable precision effect
rather than noise. BF16 was byte-exact on 7 of 8 files against FP16's 8 of 8, and
scored 20.42% WER / 4.70% CER against ground truth versus FP16's 19.72% / 4.12%.
The direction agrees with the kernel probe, where BF16 absolute error ran roughly
seven to eight times FP16's.

The threshold was 4 character edits and BF16 produced 5, so on an 8-clip corpus a
single token decides the outcome. That is stated as a limit of the corpus, not
used to soften the miss.

On speed the honest reading is that BF16 and FP16 are the same on this M3,
consistent with the kernel probe's 1.00 matmul ratio. There is no emulation
collapse here — but there is on earlier M-series parts, which is why `auto` stays
FP16 regardless.

The first block of five alternating runs was contended by unrelated desktop load;
its FP16 control moved 26.28s against 20.21s in a quiet second block, so a second
block was run and both are reported. This could not be outcome-shopping: the CER
criterion had already failed deterministically before the second block started.

BF16 also reported 13x lower peak process RSS, 0.66 GiB against 8.28 GiB. This is
**not** a memory saving. Device-side counters are identical between the arms —
3.93 GiB current-allocated in both, and driver-allocated byte-for-byte equal — so
the difference is host-page accounting during model load. It is a third
independent reproduction of the finding that RSS is the wrong instrument on this
backend.

The guard at `runtime/engine.py:100-107` accepted the flag, as expected. It
allocates one BF16 tensor and therefore detects absence of BF16 support, not
emulation of it. Since the flag is not being documented, that caveat is recorded
here rather than shipped in user documentation.

## Evidence Limitations

Three, all load-bearing.

**The released checkpoint was not measured.** The packaged default
`CohereLabs/cohere-transcribe-arabic-07-2026` is gated and the validation host has
no Hugging Face token, so every model-loading run used the third-party ungated
mirror `evewashere/cohere-transcribe-03-2026-ungated` at `29b9036c`, an older
checkpoint. These results characterize the **MPS platform path, which is
checkpoint-independent, and not the released checkpoint**. The gates that do not
load a model — the suite, the doctor, the smoke scripts, the kernel probe — are
unaffected.

**The balanced 500-file baseline is not reproducible from this repository.**
`docs/performance.md` names the five source datasets but the file selection is
not stored here, so the retained-transcript comparison that release validation
normally requires was unavailable. The substitute is self-consistency: MPS output
against CPU FP32 output over a locally assembled subset, recorded in
`reports/apple-silicon-corpus-manifest.json` with per-file hashes. The eight audio
and transcript files rebuild byte-for-byte through `scripts/build_validation_corpus.py`;
the manifest wrapping them carries a generation date and tool versions, so it is
reproducible in substance rather than byte-identical. This demonstrates
implementation stability on this platform. **It does not demonstrate parity with
the released CUDA baseline, and no such parity is claimed.**

**The corpus is the easy case.** 78 seconds of clean single-segment read speech
gives argmax the best possible conditions for stability. The finding is that the
MPS FP16 path is numerically sound on this corpus, not that it is bit-exact with
CPU FP32 everywhere. Longer audio, more segments and larger batches give FP16
rounding more chances to flip a token.

## Deferred

MPS adaptive batching and memory telemetry stay out of scope. The batch
controller reads memory only on CUDA, so `max_size` collapses to `initial` and
batch size stays static at the MPS default of 8, with OOM splitting and learned
caps still active. This cannot be fixed properly today: growth requires **peak**
allocated and reserved bytes, and PyTorch's MPS API exposes current and capacity
values with no peak counter. Feeding a current-allocation reading into a
peak-shaped budget would grow the controller against a meaningless number.
Revisit when static batch 8 plus OOM reduction is measurably insufficient on real
workloads, or when PyTorch ships an MPS peak-memory API.

Quantized checkpoints stay CUDA-gated. The arm64 bitsandbytes wheel installs and
imports but ships no MPS kernels, so the gate and its message are correct as
written.

MLX and GGUF remain unsupported. Making this model genuinely fast on Apple
Silicon means an MLX port, which is a different project.

## Release Boundary

Apple Silicon on macOS 14 or newer is supported, validated on an M3 with 24 GB
unified memory. Lower-memory and other M-series systems are compatibility
targets, not release-tested. Intel Macs are out of scope.

Every binary gate passed. No runtime source changed, which was the plan's
expected outcome rather than a shortfall: the MPS path was already correct, and
neither of the two contingent edits was authorized by a failure.

The performance numbers in `docs/performance.md` are not comparable to the RTX
3060 baselines and are not a claim of parity with them. Full-model evidence on
Apple Silicon remains manual on the M3; the `macos-latest` CI job covers
installation, the unit suite, the doctor and the kernel probe only, because the
runner cannot host the 2B model.
